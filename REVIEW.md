# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | Replaced time directly on `punch_in` with shift start hour/minute without converting to IST timezone. Furthermore, evaluated `minutes > 10` instead of `elapsed_seconds > 600`, which failed for punch-in at `09:40:01` (returning 0 instead of 10). Overnight shifts were also unhandled. | Test punch-in at `09:40:01` for shift `09:30`: returns `late_minutes: 0` instead of `10`. For UTC datetime `04:05:00Z` (09:35 IST), replacing hour with 9 resulted in negative differences. | Converted UTC instant to IST datetime, determined the attendance calendar date, calculated exact elapsed seconds from shift start, and applied whole-minute floor when `elapsed_seconds > 600`. |
| 2 | `compute_work_hours` (lines 40-41) | Used standard Python `round(..., 2)` which performs banker's rounding (round half to even) rather than the required half-up rounding (R4, R8). | Input duration yielding `2.125` hours: `round(2.125, 2)` produces `2.12` instead of `2.13`. | Implemented Decimal-based rounding using `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 3 | `compute_overtime` (lines 44-47) | Returned `max(0, minutes)` without enforcing the 30-minute minimum threshold (R3). Also did not handle overnight shifts where shift end falls on the next calendar day. | Punch-out 10 minutes after shift end yielded `overtime_minutes: 10` instead of `0`. Overnight shift (22:00-06:00) punch-out at 06:40 IST gave negative or massive incorrect values. | Added 1 day to base date for overnight shifts (`shift_end <= shift_start`), computed elapsed seconds to shift end, and returned whole-minute floor only if `>= 30`, else 0. |
| 4 | `GET /health` (lines 72-74) | Returned static `{"status": "ok"}` with 200 without checking if MongoDB is alive and responsive. Never returned 503 on database unavailability. | Stopping or disconnecting MongoDB still resulted in `GET /health` returning 200 OK. | Added `client.admin.command("ping")` inside a try-catch block, returning HTTP 503 on failure. |
| 5 | `POST /employees` (lines 78-85) | Relied on application-level `find_one` before `insert_one` (check-then-act race condition). Did not validate `shift_start != shift_end`. Stored naive local `datetime.now()` and returned internal representation instead of epoch milliseconds. | Sending simultaneous duplicate employee creations resulted in duplicate records bypassing the check. Creating an employee with `shift_start == "09:00"` and `shift_end == "09:00"` succeeded instead of returning 422. `created_at` was returned as a string/datetime instead of epoch integer. | Created a unique index on `emp_code`, caught `DuplicateKeyError` to return 409, added validation that `shift_start != shift_end` (422), and formatted `created_at` as epoch milliseconds integer. |
| 6 | `GET /employees` (lines 89-96) | Pagination skip was calculated as `skip = page * page_size`, causing page 1 to skip the first 20 records. `total` was calculated via `db.employees.count_documents({})`, ignoring the `department` filter. Results were not sorted by `emp_code`. | Requesting `page=1&page_size=20` returned items 21-40. Requesting with `?department=Engineering` returned total count of all employees in the database. Results order was non-deterministic. | Fixed skip calculation to `(page - 1) * page_size`, passed filter `q` into `count_documents(q)`, added `.sort("emp_code", 1)`, and validated `page >= 1` and `1 <= page_size <= 100`. |
| 7 | `POST /attendance/punch-in` (lines 100-121) | Check-then-insert race condition on `attendance_logs`. If employee was unknown, accessing `emp["shift_start"]` raised an unhandled `TypeError` (500). Used local server date instead of IST date (R1). Returned `id: str(res.inserted_id)` contrary to OpenAPI schema. Failed to truncate instant to whole seconds (R1). Did not enforce input schema validation on `punched_at` or `status`. | Concurrent punch-ins inserted duplicates for the same employee and date. Punching in for non-existent employee returned 500 instead of 404. Seconds-looking or string timestamps were accepted instead of returning 422. Response included extra `id` field. | Added 404 check for unknown employee, truncated timestamps to whole seconds, determined attendance date in IST supporting overnight shifts, enforced unique compound index on `(emp_code, date)` returning 409 on `DuplicateKeyError`, validated input fields with Pydantic, and returned clean `AttendanceRecord` schema. |
| 8 | `GET /attendance` (lines 124-150) | Loaded entire collection into memory with `list(db.attendance_logs.find(q))` and sorted in Python (`docs.sort(...)`), crashing on large datasets (100k records). Did not validate `date_from > date_to`. Returned `id` mapped from `_id`. Did not sort by `emp_code` ascending for tie-breaks. Returned unformatted BSON datetimes. | Calling `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` did not return 422. Calling on 100,000 documents caused high memory consumption and latency. Response objects lacked required integer epoch format for punch times. | Executed query with database-level index `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)` backed by compound index `(date, emp_code)`, added `date_from > date_to` validation (422), and converted BSON dates to epoch milliseconds without exposing internal IDs. |

### Examined and Decided Was Not a Defect

1. **`FastAPI(version="2.0.0")`**: The OpenAPI specification specifies version `2.0.0`, so keeping `version="2.0.0"` in the FastAPI initialization matches the assignment contract.
2. **Synchronous PyMongo Client**: Using synchronous `pymongo.MongoClient` alongside FastAPI endpoints is fully supported by the specification ("Motor or PyMongo") and performs efficiently with proper connection pooling and database indexes, avoiding unnecessary async overhead while meeting all latency requirements.
